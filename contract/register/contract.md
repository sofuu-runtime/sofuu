## Blocked or unverified

- **T2.3 / T2.6 / T7.3 (with `SmolLM2-360M`)** — the model never issues a tool call, so the tool-driven scenarios could not be exercised. The harnesses report BLOCKED with the attempt count; they never fabricate the event. With `Qwen-3-0.6B…Q4_K_M` the same cases run and pass. What would unblock it: a local model that reliably emits tool calls, or a harness that drives the agent's tool step without a model decision (no such surface exists today).
- **T5.6** — needs `SOFUU_TEST_CONTEXT_WINDOW` plus a provider selection for `scripts/test-real-agent-mcp.py`.
- **T7.8** — the provider-echo leak route is `unverified`: it needs a provider that answers 401 with the `Authorization` header in its body, and the runtime currently surfaces provider error bodies verbatim in the thrown error text.
- **T4.2** — the mobile/device surface needs macOS and Android runners; no device was attached.
- **T3.3 / T6.4 / T6.7 with `Qwen-3-0.6B…Q4_K_M`** — real failures, recorded rather than hidden: the two inference routes diverge after step 5, and the provider's reported token totals do not match the chunk counts the client observed for that model. Both pass with `SmolLM2-360M-Instruct-Q8_0.gguf`, which is the model the D06 register row names. The cause is outside this scope (the runtime's inference/usage accounting and `scripts/text_gate.py`).
- **T7.4 with `SmolLM2-360M`** — one suite run showed the approval resolved but the tool never ran (`T7.4: the tool actually ran` and the MCP receipt check failed) while the same case passes with `Qwen-3-0.6B…Q4_K_M`. The harness's 6 s tool deadline for the allow leg (`t73_approval_harness.js:100`) is tight when the machine is loaded; this is a candidate flake and is recorded as such, not as a pass.
- **Not run here**: the C-ABI case (T5.5) was checked against the built `dist/libsofuu.dylib` on this machine and passed; the HTTP (`kind=http`) case path in the runner has no case in the table.
