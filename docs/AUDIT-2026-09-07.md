**Scope:** the main Sofuu runtime only — `crates/sofuu-core` (~52.5k LOC), `crates/sofuu-ffi` (~3.5k), `crates/sofuu-capi` (~1.2k), `crates/ml-train` (~13.8k), embedded JS (`src/js/`), vendored C used via FFI (`deps/libuv`, `deps/quickjs`), QTSQ FFI, and build/cross/release plumbing (`build.rs`, `scripts/cross/`, `install.sh`, `.github/workflows/release.yml`).
**Excluded:** `sofuu-desktop/` and `sofuu-landing/` (per request).
**Date:** 2026-09-07. **Carry-over from AUDIT-2026-09-01-CLI:** the three architectural P0s from the prior audit are *not* re-listed — F-1 (JS_PROP_CONFIGURABLE 0x10→0x01) is fixed and re-verified this audit (see CHECKED SAFE); F-2 (multi-engine teardown) and F-3 (process-global embed config) remain open from that audit's fix order and are still live.

**Method:** clippy (deny-level) + dead-code pass; Mimosa sealed deep scan (8 findings, all triaged — appendix A); six area audits (chat/session, network/HTTP, memory/ML, process/fs/tools/MCP, JS layer, FFI/C-API/build) each reading the code directly; both P0s and every headline P1 lead-verified by hand against source before inclusion. ## P0 — memory corruption (both lead-verified against vendored libuv source)

### P0-1 · `Subprocess.write()` clobbers the uv write req — wild-pointer write + bad free on every stdin write

> **FIXED 2026-09-08** — `js_subprocess_write` now allocates the full
> `uv_req_size(UV_WRITE)` req with the payload Box hung off `req->data`
> (offset 0), payload malloc'd separately and freed in `on_write_done`,
> sync-failure path frees all three (same shape as `http_server.rs` /
> `mcp.rs write_str_dup`). Regression test `rt::process_spawn::tests::subprocess_write_delivers_payload`
> round-trips two writes through `/usr/bin/head -n 2` and asserts byte-intact
> delivery. Build clean; module tests 2/2; `cargo test -p sofuu-core --lib`
> 286/286 single-threaded.

`crates/sofuu-core/src/rt/process_spawn.rs:233-289`, with `crates/sofuu-ffi/src/uv.rs:310-439`.

The Rust mirror of libuv's write request is:

```rust
#[repr(C)]
struct WriteReq {
    req: UvWriteReq,   // uv.rs mirror holds ONLY { pub data: *mut c_void } — 8 bytes
    buf:  UvBuf,       // { base: *mut c_char, len: usize } → lands at offsets 8..24
}
```

libuv's real `uv_req_t` is `UV_REQ_FIELDS` = `{ void* data /*@0*/; uv_req_type type /*@8*/; void* reserved[6] }` (deps/libuv/include/uv.h:575 area). On every write, `uv_write2` does `uv__req_init(stream->loop, req, UV_WRITE)` at **deps/libuv/src/unix/stream.c:1363**, and on Unix `UV_REQ_INIT` is exactly `(req)->type = (typ);` (deps/libuv/src/uv-common.h:352-357) — a 4-byte enum store at **offset 8**, followed by the bufs copy.

`js_subprocess_write` populates `(*wr).buf.base/len` (offsets 8..24), `Box::into_raw`s the struct, and calls `uv_write`. Sequence, all verified in source order:

1. `uv__req_init` stores `type = UV_WRITE = 3` (enum confirmed: `UV_UNKNOWN_REQ = 0`, then `XX(REQ)`, `XX(CONNECT)`, `XX(WRITE)` → 3) into offset 8 — **the low 4 bytes of `buf.base`**, which was already populated.
2. `memcpy(req->bufs, bufs, ...)` then reads the caller's bufs array — which points at `&(*wr).buf` — *after* the clobber, so libuv's internal buffer list now holds a wild pointer (original high 4 bytes preserved, low 4 bytes = `0x00000003` on little-endian).
3. libuv writes the payload through that wild pointer.
4. The completion callback `on_write_done` runs `libc::free((*wr).buf.base as *mut c_void)` — freeing the *clobbered* value. Heap corruption / crash on essentially every `Subprocess.write()` call. The struct is also 24 bytes vs the 64-byte `uv_req_size(UV_WRITE)` requested via `sofuu_uv_write_size()`, so `type` also lands past the allocation's logical fields — the whole approach is the wrong FFI shape.

**Fix direction (for the fix pass, not applied):** adopt the pattern the codebase already uses correctly elsewhere (`http_server.rs:141-184`, `mcp.rs` `write_str_dup`): allocate the full `uv_req_size(UV_WRITE)`, heap-allocate the payload in a `Box`, store its pointer at `req->data` (offset 0 — which `uv__req_init` never touches on Unix), and read/free the Box in the completion callback. VERIFIED end-to-end against vendored libuv source.

### P0-2 · MCP disconnect: `mcp_client_close_cb` derefs `handle->data` on pipes that never had it set — wild deref on every client disconnect

> **FIXED 2026-09-08** — `js_mcp_connect` now stamps `->data` on **all four**
> handles (process + stdin/stdout/stderr pipes); the dedicated-`free_pipe_cb`
> alternative was rejected because it never decrements the `closing = 4` fence
> (stalls at 2 → client leaks) and its storage frees would double-free through
> `mcp_client_free`. `mcp_on_exit` closes all four through
> `mcp_client_close_cb`, whose stale safety comment is replaced with the real
> invariant. Regression test `rt::mcp::tests::mcp_disconnect_runs_the_close_fence`
> connects a real child (`/usr/bin/true` — macOS has no `/bin/true`), drains
> the loop, and asserts via a `#[cfg(test)]` free-counter that the fence frees
> the client exactly once. Evidence 2026-09-08: 5/5 debug runs + release-profile
> run green; full lib suite 287/287 single-threaded and 287/287 parallel (286
> prior + this test); DIFF-VERIFIED negative control — with the three pipe
> stamps reverted (pre-fix state) the test FAILS (the counter cannot increment
> unless all four close callbacks see valid `->data`). `mcp_client_test.js` 9/9
> + `mcp_server_test.js` green via `./sofuu run` on the fresh `make` binary.
> (Bin-target `session::`/`output_archive::` QTSQ tests fail pre-existing —
> verified independent by re-running one with the fix reverted: identical
> failure. Not P0-2's.)

`crates/sofuu-core/src/rt/mcp.rs:646-657 (connect), 719-722 (data init), 368-371 (exit path), 94-106 (close cb)`.

The MCP connect path mallocs three pipes (`libc::malloc(uv::sofuu_uv_pipe_size())` — note **no calloc**) and initializes `->data` on only two handles:

```rust
/* line 719 */ *(process as *mut *mut McpClient) = client_ptr;
/* line 722 */ *(stdout_pipe as *mut *mut McpClient) = client_ptr;
```

stdin_pipe and stderr_pipe never get `->data` written. But `mcp_on_exit` closes **all four** handles with the same callback (lines 368-371):

```rust
uv::uv_close(proc_h, Some(mcp_client_close_cb));
uv::uv_close(stdin_pipe_h, Some(mcp_client_close_cb));   // ->data uninitialized
uv::uv_close(stderr_pipe_h, Some(mcp_client_close_cb));  // ->data uninitialized
```

and the callback reads it back under a false safety comment (lines 94-106):

```rust
let client = *(handle as *mut *mut McpClient);
/* SAFETY: handle->data set at connect — false for the two pipes above */
```

`uv__handle_init` (deps/libuv/src/uv-common.h:331-341) sets loop/type/flags/queue/next_closing and **never zeroes `->data`** — for the process handle it happens to be set (719), for stdout_pipe it's the same pointer anyway, but for stdin/stderr it is *stale malloc garbage* (malloc, not calloc). On every MCP client disconnect (the normal "server exited" path, success path — the uv_spawn-failure path uses `free_pipe_cb` and is safe) the close callback dereferences a wild pointer into `McpClient` fields and closes/frees through it.

**Fix direction:** either initialize `->data` on all four handles at connect, or give stdin/stderr a dedicated `free_pipe_cb` (the failure path's callback already does the right thing).

## P1 — by area (17)

### Network / HTTP / streaming

**P1-1 · `tool_calls_fn` JSValue leaked on every `ai.stream()` call** — `crates/sofuu-core/src/rt/ai.rs:3448-3492` (VERIFIED). The function takes local refs to five callbacks off the factory, dups them into the request box, then frees only `push_fn / done_fn / error_fn / think_fn` (3489-3492) — `tool_calls_fn` (taken at 3452, duped at 3471) is never freed. One live JSValue ref per stream, every turn, forever. The CURLM-fail early return (3515-3527) frees only the four dup'd members and also leaks the local `iterator` ref; on the success path `iterator` is returned to JS so ownership transfers correctly (3543, VERIFIED).
**FIXED 2026-09-08** — both leak sites closed in `js_ai_stream`: (1) success path now frees all five local refs (`tool_calls_fn` included) before curl setup; (2) the CURLM-fail early return additionally frees the box's `tool_calls_fn` dup and the local `iterator` ref. Regression test `rt::ai::tests::stream_error_path_does_not_retain_factory_objects` drives 2+8 full streams through the live event loop against 127.0.0.1:1 (connect-refused), settles each via for-await/catch, and asserts the GC'd `obj_count` delta stays flat (`JS_ComputeMemoryUsage`); negative control (local `tool_calls_fn` free removed) failed with exactly +2 retained objects per stream (delta 16/8), restore → passes. Gates: `cargo test -p sofuu-core --lib` 316/316, `make` clean, JS suite 28/0/1. The CURLM-fail path itself is not externally reachable (needs `CURLM_RECURSIVE_API_CALL` re-entrancy from inside the curl stack) — covered by symmetry in the same fix.

**P1-2 · Transfer-error path never parks a GC'd-mid-transfer Response — accumulating leaks up to ~256MB each** — `crates/sofuu-core/src/rt/http_client.rs:1096-1140`. Only the DONE path parks a Response whose JS side was finalized while its transfer ran. On the error path the parked buffer (up to `AI_MAX_RESPONSE`-scale body) is dropped unheld → unreclaimable. A few failed large fetches per process = retained hundreds of MB.
**FIXED 2026-09-08** — the error branch of `check_multi_info_global` now parks a `finalized` Response exactly like the DONE path (`reclaim_orphan_resp()` + `ORPHAN_RESP.set(resp)` + `(*req).resp = null`), so the body buffer is freed at the next fetch entry after every reader microtask has drained. Regression test `rt::http_client::tests::transfer_error_parks_gc_d_mid_transfer_response`: a 3-connection choreography server holds `/x` mid-transfer (`Content-Length: 100`, 7 bytes sent) while the JS drops the resolved Response and runs `__run_gc()` (finalizer runs with done==0 → deferred), then a `/signal` fetch kills conn 0 → `CURLE_PARTIAL_FILE` error path; asserts the choreography completes, then GC + `reclaim_orphan_resp()` + `RESPONSES.len()==0`. The end-of-test reclaim is required because curl can drain `/signal`'s DONE one socket-action pass before `/x`'s error, making the park postdate `fetch('/y')`'s entry reclaim — a genuine ordering insight captured in the test comment. Negative control (park block removed) failed with exactly `RESPONSES.len()==1` (the leaked finalized ResponseData), restore → passes. Gates: `cargo test -p sofuu-core --lib` 317/317, `make` clean, JS suite 28/0/1 (one `chat_chip_e2e.sh` mock-startup flake in-suite; passes standalone exit 0).

**P1-3 · Redirected fetch resolves with the FIRST 3xx status + merged headers, not the final response** — `http_client.rs:981-996`.
> **FIXED 2026-09-08** (SSRF-family unit): FOLLOWLOCATION is OFF and redirects are re-issued manually by `check_multi_info_global`/`redirect_reissue` — the promise resolves only on the final non-3xx response (or finalizes with its own status when a 3xx has no Location, e.g. 304). Also caught+fixed a NEW production bug the tests exposed: after a rejected redirect hop (too many hops / invalid Location / refused scheme) the fall-through finalize re-resolved the already-freed promise handle (double-settle UAF → SIGSEGV; promise handles are freed by their one-shot settle per `promise.rs`); gated on a `rejected` flag. **P1-4 · `stream_check_cb` holds a `RefCell` borrow across JS execution → abort on GC during constructor call** — `http_client.rs:1028-1045`. `borrow()` is still live when `JS_CallConstructor` runs; if a GC finalizer settles a `done=1` Response that calls `.borrow_mut()` on the same cell → `BorrowMutError` panic abort of the runtime.
> **FIXED 2026-09-08** — `stream_check_cb` now snapshots a worklist of (ctx, resp, settle) under the borrow and DROPS the borrow before any JS runs: each candidate is re-validated with `is_live_response` (an earlier work item's GC can free a later one), fulfilled outside the borrow, and `pending_settle` is nulled during the snapshot so a finalizer running mid-fulfillment can never double-settle (same one-shot promise-handle contract as the P1-3 redirect fix). Safety analysis of the freed-response path: `response_next_chunk` pops the chunk BEFORE the constructor and never touches `r` after it; `response_fulfill_pending` nulls `pending_next`/`pending_resolve` before the constructor and never derefs `r` after — a Response collected mid-fulfillment is harmless and the chunk is still delivered. Regression test `stream_check_gc_during_constructor_no_borrow_abort` replaces `globalThis.Uint8Array` with a one-shot wrapper that drops the Response's last reference (`hold = null`) + runs `__run_gc()` INSIDE the first constructor call — which is exactly the chunk-fulfillment constructor under `stream_check_cb` (server choreography: headers flush, 150ms hold so `pending_next` arms, then body with Content-Length satisfied + EOF in one socket pass so `done==1` is set before the uv_check fires and the finalizer takes the borrow_mut path); asserts state `gc-in-ctor;chunk:7;done:0;` (GC provably in-ctor AND the chunk still delivered after the mid-fulfill GC) and `RESPONSES.len()==0`. Negative control (original inline-borrow body restored): test panics with `RefCell already borrowed` at `http_client.rs:152` — the finalizer's own `borrow_mut`, proving the panic fires under the still-live callback borrow; fix restored → passes (5/5 deterministic). Gates: `cargo test -p sofuu-core --lib` 318/318, `make` clean, JS suite 29/0/1 (total 30 — the SSRF session's `web_guard_test.js` entry included).

Gates: `cargo test -p sofuu-core --lib` 325/325 (11/11 http_client incl.), `make` (./sofuu 2.9M / 3,086,400 B), JS 29/0/1 of 30 (one in-suite `chat_chip_e2e.sh` timing flake, passes standalone and on suite re-run).

### Memory / ML

**P1-6 · `Vec::with_capacity(n_hints)` with no clamp — hostile hint count → ~17GB reservation → allocator abort** — `crates/sofuu-core/src/rt/memory.rs:1827` (and the same shape in `js_kv_search` ~2022-2026). Every sibling path clamps to 1024; this one takes the JS-provided count raw. `memory.open(...)` / kv search with a large `n_hints` argument is an instant OOM kill. > **FIXED 2026-09-08**: `js_kv_search` clamps `n_hints` to 1024 at the JS boundary, mirroring the sibling CMA-hints clamp (memory.rs ~1127).
